Prompt version: codex-hygiene-v1

You are reviewing data-catalog hygiene for a dbt project. Inspect the workspace, prioritize at most five findings, act on them within the rules below, and return the final answer as JSON matching the provided output schema.

## Task
- Trigger: remediation (find and fix existing hygiene debt).
- Asset scope: ["daily_revenue"]

## Workspace (the current directory)
- `project/`: a dbt project (dbt-duckdb), already built; `project/target/` holds dbt's manifest and other artifacts.
- `project/catalog/catalog.json`: the data catalog. An asset's catalog metadata is its entry there with `project/catalog/overrides.json` `assets.<asset>` (if present) merged over it.
- `warehouse.duckdb`: the DuckDB warehouse with the built seeds and models (schema `main`).

## Tools
- `dbt` (run from `project/`; the profile is configured, e.g. `dbt parse`, `dbt ls`, `dbt compile`, `dbt test`).
- `python` with the `duckdb` package; open the warehouse read-only, e.g. `duckdb.connect('warehouse.duckdb', read_only=True)`.
- Standard shell utilities. There is no network access.

## Rules
- Work only inside this workspace. Do not read or write files outside it.
- Do not use evaluation ground truth, invent business meaning, or exceed five prioritized findings.
- Keep data queries bounded (at most 10000 rows) and do not modify the warehouse.
- The only file you may change is `project/catalog/overrides.json`, and only the fields ["canonical", "description", "grain", "lifecycle", "owner"] of assets in scope. Do not change SQL, dbt YAML, seeds or any other file.
- Use only the issue types below. Each finding's action class must be one the issue allows; `required_evidence` names the facts a finding must rest on, which you establish from workspace files, dbt artifacts or bounded queries.

## Actions
- `patch`: you write the change to `project/catalog/overrides.json` yourself, then report it with operation `update_catalog_field`, the `field` and new `value`, and `verification` `{"field": <field>, "equals": <value>}` stating what the catalog field must equal afterwards.
- `propose`: a reviewable proposal with no file change; operation `propose_metadata_change` or `request_review`.
- `report`: a finding only, no change; operation `report_only`.
- For `propose` and `report`, set `field`, `value` and `verification` to null.

## Output
- `findings`: at most five, highest priority first. `asset` must be an asset in scope.
- `evidence`: one entry per fact: `kind` `file` with `source` a workspace-relative path such as `project/models/example.sql`, or `kind` `command` with `source` the exact command you ran; `fact` states what it shows.
- `changes_made`: every file you changed and why (empty if none). `verification_performed`: commands you ran to check your work and their results.
- `unresolved_questions`: decisions that need a human reviewer.
- If there is no hygiene issue, return an empty `findings` list.
